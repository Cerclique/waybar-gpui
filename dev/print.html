Writing a panel

A panel is a GPUI view. Your program registers one or more panels and hands control to the SDK, which turns a click on a bar module into a popover showing the panel.

The smallest program

use waybar_gpui::{card, gpui::{prelude::*, Context, Window}, Panel};

struct Hello;

impl Panel for Hello {
    const NAME: &'static str = "hello";
    fn new(_args: &[String], _window: &mut Window, _cx: &mut Context<Self>) -> Self {
        Hello
    }
}

impl Render for Hello {
    fn render(&mut self, _window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement {
        card(cx).child("Hello")
    }
}

fn main() -> std::process::ExitCode {
    waybar_gpui::Program::new("my-panels").panel::<Hello>().run()
}

The starter template generates exactly this (see the README).

  • Panel::NAME is what a bar module’s on-click names: my-panels toggle hello.
  • Panel::new builds the panel each time its popover opens. The panel is dropped when the popover closes; nothing is kept between opens (see Live data and state for what to do instead). args are the panel arguments.
  • Render is plain GPUI. card(cx) gives the standard rounded, bordered, themed rectangle; it’s optional (Theming).
  • Program::new(id) names your program. The program ID names its socket, its log file and its Hyprland layer namespace, so pick it once and keep it. It must match ^[a-z0-9][a-z0-9-]*$; anything else panics at start.
  • .panel::<P>() registers a panel; two panels with the same NAME panic.
  • .run() owns the command line: toggle, close, quit, preview, daemon, help. Run your program with no arguments to see the usage and an on-click line per panel. If you want commands of your own, handle them in main before calling run.

GPUI

The SDK re-exports GPUI as waybar_gpui::gpui; don’t add gpui (or gpui-pre) to your own Cargo.toml, or you’ll get two copies that don’t fit together. GPUI is pre-1.0 and the SDK pins an exact snapshot: the SDK’s API and GPUI’s are on docs.rs, and cargo doc --open in your project shows both offline.

GPUI’s derive macros (#[derive(IntoElement)] and friends) expand to paths starting with gpui::. In any module that uses them, bring the name into scope:

use waybar_gpui::gpui;

workspace.rs in the example panels shows a #[derive(IntoElement)] row.

Size

Don’t declare a size. The card fits its content and is placed next to the clicked bar module, centred on the cursor. Cap it yourself if it can grow, and scroll the overflow:

card(cx)
    .w(gpui::px(340.))
    .max_h(gpui::px(420.))
    .child(div().id("rows").flex().flex_col().overflow_y_scroll().children(rows))

The runtime also keeps the card inside the monitor’s usable area; past that, scrolling is up to you. When content grows while the popover is open, the card is re-placed on the next frame.

Several panels

One program can hold many panels:

waybar_gpui::Program::new("my-panels")
    .panel::<Clock>()
    .panel::<Volume>()
    .run()

Only one popover is open at a time, across all programs: opening one closes the other.

Panel arguments

The words after the panel’s name in on-click are its panel arguments, handed to Panel::new as &[String]:

"custom/clock-paris": { "on-click": "~/.cargo/bin/my-panels toggle clock Paris 1", … },
"custom/clock-tokyo": { "on-click": "~/.cargo/bin/my-panels toggle clock Tokyo 9", … },

impl Panel for ClockPanel {
    const NAME: &'static str = "clock";

    fn new(args: &[String], _window: &mut Window, _cx: &mut Context<Self>) -> Self {
        let label = args.first().cloned().unwrap_or_else(|| "UTC".into());
        let offset_hours = args.get(1).and_then(|s| s.parse().ok()).unwrap_or(0);
        Self { label, offset_hours }
    }
}

Full example: clock.rs.

  • You parse them. The SDK passes plain strings; decide your own defaults and what to do with bad input (fall back, or show an error in the card).
  • Toggle compares them. A click closes the popover if the same panel with the same arguments is open; otherwise it opens the panel with the new arguments. So “Paris” and “Tokyo” are two different popovers of one panel.
  • Words, not a shell string. Waybar runs on-click through /bin/sh -c, so quoting works as in a shell (toggle note "two words"). Arguments can’t contain tabs or newlines.
  • preview takes them too: cargo run -- preview clock Tokyo 9.

Live data and state

The SDK adds nothing here: it’s plain GPUI. Two facts shape everything:

  • A panel is built when its popover opens and dropped when it closes.
  • Your program’s daemon stays running between opens, until quit or logout.

So: work tied to one open belongs to the panel; anything that must outlive a close belongs to the daemon, in a GPUI Global.

Updating while open

Store the Task in a field. Dropping the panel drops the task, which stops it; there’s nothing to clean up.

From a timer, as in clock.rs:

pub struct ClockPanel {
    _tick: Task<()>,
    // …
}

and in Panel::new:

let _tick = cx.spawn(async move |this, cx| loop {
    cx.background_executor().timer(Duration::from_secs(1)).await;
    if this.update(cx, |_, cx| cx.notify()).is_err() {
        return; // the panel is gone
    }
});

From a blocking source (a socket, a pipe, a D-Bus call), as in workspace.rs, which follows Hyprland’s event socket: block on a background thread, update on the foreground one. (hypr is the example’s own small Hyprland client, hypr.rs; the SDK doesn’t provide one, so bring your own or a crate.)

let _events = cx.spawn(async move |this, cx| {
    let Ok(mut events) = hypr::Events::connect() else { return };
    loop {
        let (back, event) = cx
            .background_executor()
            .spawn(async move { let event = events.next(); (events, event) })
            .await;
        events = back;
        let Some(Ok(_event)) = event else { return };
        if this.update(cx, |panel, cx| { panel.refresh(); cx.notify(); }).is_err() {
            return;
        }
    }
});

After the popover closes, a background read that is already waiting keeps its thread until the next event arrives; then the update fails and the loop ends. That’s harmless for event streams that tick often. For sources that can stay silent for a long time, prefer a timeout or a non-blocking API.

State that survives a close

Put it in a GPUI Global. It lives in the daemon, so it’s there on the next open, until the daemon quits (or is replaced by a rebuilt binary, see Dev loop).

#[derive(Default)]
struct Opens(u32);

impl Global for Opens {}

and in Panel::new:

let opens = {
    let opens = cx.default_global::<Opens>();
    opens.0 += 1;
    opens.0
};

clock.rs counts its opens this way. For anything that must survive the daemon too (settings, history), write it to a file yourself.

Theming

The runtime paints nothing: the popover’s surface is transparent, and the card is whatever your panel draws. The SDK gives you two opt-in pieces.

Theme

A plain struct of colours, stored as a GPUI global and read with Theme::get(cx). The default is Catppuccin Mocha.

FieldUsed for
baseCard background (translucent by default).
surfaceRaised rows, selected items.
overlayBorders, hover.
textMain text.
subtextSecondary text.
accentHighlights, focus rings, primary buttons.

Give your program its own by changing the default’s colours. (Theme may gain colours in a later release, so a Theme { … } literal doesn’t compile.)

use waybar_gpui::{gpui::{rgb, rgba}, Theme};

let mut theme = Theme::default();
theme.base = rgba(0x2e3440f0);
theme.accent = rgb(0x88c0d0);
waybar_gpui::Program::new("my-panels").theme(theme).panel::<Hello>().run()

Use it in your panels so they follow it:

let theme = Theme::get(cx);
div().text_color(theme.subtext).child("secondary")

card()

card(cx) returns a div with the standard chrome: a column with gaps and padding, rounded corners, a 1 px overlay border, base background, text colour, small text. It’s a starting point you can chain onto (card(cx).w(px(300.))), or skip entirely and draw your own shape: the runtime places whatever your panel’s root element is.

Waybar’s style

Your panels don’t read Waybar’s style.css; match its colours through Theme. The optional Hyprland rule in Installing adds blur behind the card.

With the components feature, Theme also colours gpui-component’s widgets.

Components

gpui-component is a widget library for GPUI: buttons, switches, inputs, dropdowns, lists. The SDK offers it behind an opt-in feature:

waybar_gpui = { version = "0.2.0", features = ["components"] }

(The starter template asks “Use gpui-component widgets?” and writes this for you.) It’s then available as waybar_gpui::components; don’t depend on gpui-component yourself, for the same reason as GPUI.

use waybar_gpui::components::{button::{Button, ButtonVariants as _}, switch::Switch};

card(cx)
    .child(Switch::new("wifi").checked(self.wifi).on_click(cx.listener(|this, on, _, cx| {
        this.wifi = *on;
        cx.notify();
    })))
    .child(Button::new("done").primary().label("Done").on_click(|_, _, cx| close(cx)))

Full example with switches and a dropdown: controls.rs.

What the runtime does for you

  • Initialises the library and registers its icon assets.
  • Copies your Theme into gpui-component’s theme at startup, so widgets match your cards. Adjust gpui-component’s theme in code afterwards if you want finer control.

What works, what doesn’t

  • Works: widgets, menus and dropdowns, in-window popovers. A menu may overflow the card; clicking it doesn’t dismiss the popover.
  • Doesn’t: gpui-component dialogs and notifications. They need its Root view, which on Linux draws a window border and shadow around layer surfaces and veils the whole monitor, so the runtime doesn’t use it. Build a “dialog” as a second view inside your panel instead.

Costs

About 110 more crates to build and ~10 MB more binary. Programs without the feature pay nothing.

Versions

gpui-component is pinned exactly, together with GPUI: the three pins always move together, and each move is a breaking SDK release (see Limits).

Closing and Esc

How a popover closes

What happensWho decides
A click on the backdrop (anywhere outside the card, on any monitor, the bar included)Always closes; a panel can’t prevent it.
EscThe panel first, if it has focus (below). Otherwise closes.
The panel calls close(cx)The panel.
A click on the bar, the same bar module includedCloses, as a backdrop click (see the note below).
Another popover opens (any program)The old one closes first: one popover at a time.

Note: while a popover is open, the backdrop covers Waybar on every monitor, so Waybar can’t be clicked. Clicking the bar (the same bar module or another, on any monitor) is a click on the backdrop: it only closes the popover. A second click opens the new panel. See How it works.

Closing from the panel

Call close(cx) from any event handler, typically after doing the thing the user clicked:

div()
    .id("row")
    .on_click(move |_, _, cx| {
        std::process::Command::new("hyprctl").args(["dispatch", "…"]).spawn().ok();
        close(cx);
    })

The close is deferred until the current event finishes, so it’s safe inside the panel’s own handlers.

Actions are yours. The SDK only provides what needs the runtime (closing the popover). Running commands, Hyprland dispatches, D-Bus calls are your own code: std::process::Command, a client crate, anything.

Esc

Esc goes to the focused element first and bubbles up to the runtime, which closes the popover. To handle keys yourself:

  1. Focus one of your elements in Panel::new (otherwise nothing of yours has focus and Esc goes straight to the runtime).
  2. Handle the key; call cx.stop_propagation() to keep the popover open.
fn new(_args: &[String], window: &mut Window, cx: &mut Context<Self>) -> Self {
    let focus = cx.focus_handle();
    window.focus(&focus, cx);
    Self { focus, editing: false }
}

and in render:

card(cx)
    .track_focus(&self.focus)
    .on_key_down(cx.listener(|this, event: &gpui::KeyDownEvent, _, cx| {
        if event.keystroke.key == "escape" && this.editing {
            this.editing = false;
            cx.notify();
            cx.stop_propagation(); // first Esc leaves edit mode, the popover stays
        }
    }))

clock.rs does this with an edit mode (e enters it, the first Esc leaves it, the second closes).

Your panel can’t stop a backdrop click: with Waybar unclickable while a popover is open, that guarantees the user can always get out.

Using a coding agent

GPUI is pre-1.0, so a coding agent’s memory of its API is usually wrong for the snapshot the SDK pins, and it knows little about waybar_gpui. The repository ships an agent skill, skills/waybar-gpui/SKILL.md, that sets it straight. It holds no API of its own: it makes the agent find your project’s waybar_gpui and GPUI versions, then read the guide, the SDK’s source and GPUI’s source for exactly those versions. It also tells it:

  • the words to use (panel, bar module, popover…: the glossary);
  • the steps to add a panel, ending in preview;
  • to check your Waybar and Hyprland versions before editing their config;
  • to warn you before running preview or toggle, which open popovers on your screen.

One file serves every version: an old copy keeps working after you upgrade the SDK, and the guide for your version wins wherever the two disagree.

Claude Code

Copy the skill into your program’s repository, so everyone working on it gets it:

mkdir -p .claude/skills/waybar-gpui
curl -fsSL -o .claude/skills/waybar-gpui/SKILL.md \
  https://raw.githubusercontent.com/Cerclique/waybar-gpui/v0.2.0/skills/waybar-gpui/SKILL.md

or into ~/.claude/skills/waybar-gpui/ for all your projects. Claude Code uses it on its own when you work on a panel; /waybar-gpui invokes it by hand.

Other agents

Agents that read skills (SKILL.md with a name and description) take the same file in their own skills folder. For the rest, save it anywhere in the repository and point the agent’s instructions file at it, e.g. in AGENTS.md:

Before working on a panel, read and follow `docs/waybar-gpui-skill.md`.

Dev loop

Preview, no Waybar needed

cargo run -- preview hello            # or: preview clock Tokyo 9

preview opens the panel at your cursor, logs to the terminal, and exits when the popover closes (Esc, a click outside, or close(cx)). It doesn’t touch your program’s running daemon, but it does close any open popover first. It has no socket, so the reverse doesn’t hold: a toggle from a keybind or script, or another program opening its popover, can’t close a preview, and you get two popovers. (Clicks still close it, like any popover.) Exit status: 0 after a normal close, 1 if the panel couldn’t open, 2 for a bad command line.

To rebuild and reopen on save, let a file watcher restart the preview, for example watchexec or cargo-watch:

watchexec -r -e rs -- cargo run -- preview hello
cargo watch -x 'run -- preview hello'

On your real bar

Point a bar module at your build directly:

"custom/hello": {
  "exec": "echo hello",
  "interval": "once",
  "on-click": "/path/to/your-repo/target/debug/my-panels toggle hello",
},

Then just cargo build and click: a daemon started from an older binary replaces itself on the next click, so you never need to stop it by hand. This also works between a target/debug build and an installed copy with the same program ID: whichever one a click runs takes over. my-panels quit remains if you want the daemon gone.

Logs

A daemon started by a click logs to ~/.local/state/waybar-gpui/<id>.log ($XDG_STATE_HOME/waybar-gpui/<id>.log), emptied each time a click starts a new daemon:

tail -f ~/.local/state/waybar-gpui/my-panels.log

Everything written to stderr lands there: the runtime’s lines (my-panels: opened hello on DP-1 (Top bar), my-panels: closed hello (escape)), your eprintln!, any logger you set up (env_logger, tracing-subscriber), and panic messages. preview, and daemon run by hand, log to the terminal instead. The SDK has no logging dependency; use whatever you like.

Panics

A panic in your panel takes the daemon down: the popover disappears and the panic message is in the log. The next click starts a fresh daemon. Nothing else to do.

Example panels

This repository’s examples/example-panels is a program built the way yours is, with one panel per pattern. Clone the repo and run make dev to get a second Waybar wired to them, or cargo run -p example-panels -- preview clock Paris 1.

Installing

Build and install

In your program’s repository:

cargo install --path . --locked

This puts the binary in ~/.cargo/bin. Commit your Cargo.lock so --locked installs exactly what you tested. To update later, pull and run the same command: the next click replaces the running daemon with the new binary, with no Waybar reload.

Waybar

Run your program with no arguments: the usage text ends with a ready-to-paste on-click line per panel, using the real path of the binary:

panels and their Waybar on-click lines:
  hello        "on-click": "/home/me/.cargo/bin/my-panels toggle hello"

Waybar started by Hyprland usually doesn’t have ~/.cargo/bin on its PATH, so use the full path. ~ works too: Waybar runs on-click through /bin/sh -c. A bar module for it, in ~/.config/waybar/config.jsonc:

"modules-right": ["custom/hello", …],

"custom/hello": {
  "exec": "echo hello",        // what the bar shows; any custom/* program works
  "interval": "once",
  "exec-on-event": false,      // no need to re-run exec after a click
  "on-click": "~/.cargo/bin/my-panels toggle hello",
},

The bar module’s own output (exec, format, styling) is ordinary Waybar custom/* configuration (man 5 waybar-custom); the SDK only handles the popover. If ~/.cargo/bin is on Waybar’s PATH, the bare name works: "on-click": "my-panels toggle hello".

After editing the config, reload Waybar: pkill -SIGUSR2 waybar.

Hyprland

Nothing is required: the popover is a layer surface that places itself. One optional rule, for every waybar-gpui program at once, adds blur behind the card and a fade (Hyprland 0.55+ Lua config, ~/.config/hypr/hyprland.lua):

hl.layer_rule({
  match = { namespace = "^waybar-gpui:" },
  blur = true,
  ignore_alpha = 0.3,   -- blur only the card, not the transparent rest
  animation = "fade",
})

For one program only, match ^waybar-gpui:<id>$.

Uninstalling

Stop the daemon first, or it keeps running from the deleted binary until you log out:

my-panels quit
cargo uninstall my-panels

Then remove the bar modules from your Waybar config.

For your users

People installing your program need the same steps without the Rust: link Using a waybar-gpui program from your README (the starter template’s README already does).

Using a waybar-gpui program

This page is for people who install a program built with waybar-gpui (say, my-panels) to get popovers on their Waybar. You don’t need to write Rust. Requirements: Hyprland, Waybar, a Rust toolchain to build it, and a working Vulkan driver.

Install

Follow the program’s own instructions; usually:

git clone <the program's repository> && cd <it>
cargo install --path . --locked

Add it to Waybar

Run the program with no arguments. It lists its panels, each with the line to paste into a Waybar bar module:

panels and their Waybar on-click lines:
  clock        "on-click": "/home/me/.cargo/bin/my-panels toggle clock"

In ~/.config/waybar/config.jsonc, add a bar module and put it in a modules-* list:

"custom/clock": {
  "exec": "echo clock",
  "interval": "once",
  "exec-on-event": false,
  "on-click": "/home/me/.cargo/bin/my-panels toggle clock",
},

Keep the full path: Waybar usually can’t find programs in ~/.cargo/bin by name. Some panels take extra words after their name (toggle clock Paris 1); the program’s README says which. Reload Waybar with pkill -SIGUSR2 waybar.

Optional, in ~/.config/hypr/hyprland.lua, for blur behind every waybar-gpui popover:

hl.layer_rule({ match = { namespace = "^waybar-gpui:" }, blur = true, ignore_alpha = 0.3, animation = "fade" })

Using it

  • Click the bar module: the popover opens next to it.
  • Close it with Esc, a click anywhere outside it, or a click on the bar.
  • While a popover is open, the first click elsewhere only closes it: clicking another bar module, on any monitor, takes a second click. That’s by design: the popover holds the keyboard while it’s open, so the first click outside closes it rather than reaching what’s below.
  • Only one popover is open at a time, even across different programs.
  • The first click after login takes a moment longer (the program starts in the background); later ones are fast.

When something is wrong

  • Nothing opens: check the path in on-click (run it in a terminal), and read the log: ~/.local/state/waybar-gpui/<program>.log.
  • It still shows an old version after an update: click again; a click replaces an outdated background process. my-panels quit stops it outright.
  • Uninstall: my-panels quit, then cargo uninstall my-panels, then remove the bar module.

How it works

What happens between a click and a popover, at the level an author needs to understand what they see. The full picture, with the reasons and the evidence, is in docs/architecture.md.

One binary, two roles

Your program is both the click client and a daemon:

sequenceDiagram
    participant W as Waybar
    participant C as my-panels toggle hello
    participant D as my-panels daemon
    W->>C: on-click runs it
    alt no daemon yet (first click)
        C->>D: start it in the background
        D->>D: open the popover
    else daemon running
        C->>D: toggle hello (Unix socket)
        D->>D: open the popover, or close it if hello is open
    end
    Note over C: exits right away
    Note over D: stays running: GPU and fonts stay loaded
  • The first click starts the daemon, so it’s slower (a few hundred ms); later clicks only open a window and are fast.
  • The daemon lives until my-panels quit or logout. If the binary on disk changed (you rebuilt or reinstalled), the next click replaces the daemon.
  • The daemon’s socket is $XDG_RUNTIME_DIR/waybar-gpui/<id>.sock, named by your program ID. Every program’s socket is in that one directory, which is how programs close each other’s popovers: at most one is open at a time. Next to it, an empty <id>.lock is used only while a daemon starts, so two clicks at once start one daemon, not two; it stays there, and that’s normal.

The popover is a full-screen, transparent layer

Wayland doesn’t let one program attach a real popup to another program’s window, so the popover can’t hang off Waybar’s icon. Instead:

  • The popover is a transparent layer surface covering the whole monitor the click came from, bar included, above everything else.
  • Your panel is drawn inside it as the card, placed next to the bar: centred on the cursor, 6 px off the bar edge, kept inside the screen. Top, bottom, left and right bars all work.
  • The rest of the surface is the invisible backdrop, and every other monitor gets a transparent surface of its own that extends it. A click on the backdrop, on any monitor, closes the popover.
  • It takes the keyboard exclusively, so Esc always works.

While a popover is open, the keyboard stays with it, so it must not stay open after a click elsewhere. That’s why the backdrop covers every monitor, Waybar included: Waybar can’t be clicked while a popover is open, and the first click outside only closes it. See Closing and Esc.

Panels are fresh on every open

The daemon builds your panel when the popover opens and drops it when it closes. Live updates and state that outlives a close are plain GPUI patterns: Live data and state.

Logs

A daemon started by a click writes its stderr to ~/.local/state/waybar-gpui/<id>.log; see Dev loop.

Limits

By design

  • Hyprland only. Placement and click handling depend on Hyprland’s IPC and how it routes input to layer surfaces. Other compositors (Sway, niri…) aren’t supported.
  • Waybar can’t be clicked while a popover is open. The first click outside the card only closes the popover; clicking another bar module takes a second click. It comes from how Hyprland routes clicks; nothing in the SDK can change it.
  • One popover at a time, across all programs.
  • Placement is fixed: next to the bar, centred on the cursor. Panels don’t choose an alignment or an offset.
  • Panels don’t open other panels. Only bar-module clicks (or toggle from a script or keybind) open panels; several views inside one panel are plain GPUI state.
  • No gpui-component dialogs or notifications (they need its Root, which breaks layer surfaces). Menus and in-window popovers work. See Components.
  • Other exclusive surfaces (rofi, fuzzel, wlogout) opened over a popover interact awkwardly: moving the pointer can hand the keyboard back to the popover, and a full-screen one blocks it until it closes.
  • The theme is set in code (Program::theme): people who install a program can’t restyle it with a theme file.
  • The SDK covers the popover, not the bar. What the bar module shows is ordinary Waybar custom/* configuration.

Versions

  • The SDK is on crates.io: waybar_gpui = "X.Y.Z" in your Cargo.toml. Each release is also tagged vX.Y.Z in the repository; the starter template uses the tag, and the guide’s site shows the latest release.
  • 0.x semver: a breaking change bumps the minor version (v0.1.x → v0.2.0); fixes bump the patch.
  • GPUI (gpui-pre) and gpui-component are pinned exactly, and move together. Every change to those pins is a breaking release, with the new versions in the changelog. Upgrade deliberately, and keep your Cargo.lock.
  • Tested with Hyprland 0.57 (Lua config), Waybar 0.15 and the Rust in rust-toolchain.toml; the oldest Rust that builds it is 1.95 (rust-version, checked in CI). GPUI renders with Vulkan.

Troubleshooting

Investigating

For a problem the table doesn’t list, start with what the runtime logs. Where the log is depends on how the daemon started: see Dev loop.

  • Read the runtime’s lines first. Each open logs <id>: opened <panel> on <monitor> (<edge> bar), each close <id>: closed <panel> (<reason>), and a failed open <id>: cannot open <panel>: <error> (a panel’s arguments follow its name, e.g. clock ["Paris"]). They tell you whether the popover opened, on which monitor, and why it closed.
  • Get the output in the terminal. <program> preview <panel> opens the panel at your cursor and logs to the terminal, without Waybar.
  • Run the daemon in the foreground. <program> quit, then <program> daemon <panel>: the daemon logs to the terminal, and clicks on the bar module reach it if its on-click runs the same executable (another one replaces it). Run quit first: while a daemon runs, a hand-run daemon exits with <id>: daemon already running.
  • Tell Hyprland from GPUI. While the popover is open, hyprctl layers lists its surface as namespace: waybar-gpui:<id> and a backdrop on each other monitor as namespace: waybar-gpui-backdrop:<id>. A surface that is listed but shows nothing points at drawing (GPUI); no surface points at the open itself (look for cannot open in the log). hyprctl monitors and hyprctl cursorpos show what placement used: the popover opens on the monitor under the cursor, next to its bar.

Reporting a bug

Open an issue with the bug report template. It asks for what happened, the steps to reproduce, the relevant log lines, your waybar_gpui, Rust, Hyprland and Waybar versions, whether the components feature is on, and your distribution and GPU.

Tip: reproduce with <program> preview <panel> if you can. The output lands in the terminal, ready to paste.

Waybar GPUI popovers

Clicking an item in Waybar opens a small GPUI UI next to it. This repo provides what makes that work and lets authors write the UI themselves.

Language

What the person at the bar sees

Bar module: An item in Waybar (a custom/* entry): its icon or text, plus the on-click that toggles a panel. Avoid: module (alone), plugin, widget

Popover: A panel while it is on screen, placed next to the clicked bar module. At most one is open at a time, across all programs. Avoid: popup, window

Card: The visible rectangle of a popover, sized to the panel’s content, where the panel is drawn. Avoid: frame, window

Backdrop: The invisible area around the card, on every monitor; a click that lands on it dismisses the popover. Avoid: overlay, background

Dismiss: Closing a popover from outside the panel: Esc the panel doesn’t handle, or a click on the backdrop. Avoid: hide, cancel

Toggle: What a bar module’s click asks for: open the panel, or close it if the same panel with the same panel arguments is already open. Avoid: show, open (when closing is also meant)

What an author builds

Author: Someone writing their own panels with the SDK, in their own repository. Avoid: user (ambiguous with the person clicking the bar)

Panel: The GPUI UI an author writes, built fresh each time its popover opens. Avoid: module, plugin, popup, view

Panel arguments: The words after the panel’s name in a bar module’s on-click, handed to the panel when it opens. Avoid: options, parameters, config

Preview: Opening a panel from a terminal, without a bar module, until it is dismissed. Avoid: demo, test mode

Program: An author’s executable that registers one or more panels; each program runs its own runtime. Avoid: binary, app, plugin

Program ID: The stable name an author gives their program, by which programs tell each other apart. Avoid: app id, socket name

Theme: The colours a program’s cards, panels and widgets share. Avoid: style, palette

SDK: The Rust crate authors build panels and programs against. Avoid: API, framework, library (as a name for it)

waybar-gpui: This project as a whole: the SDK, its runtime and the guide. The SDK’s crate alone is waybar_gpui. Avoid: waybar_gpui (except for the crate)

What makes it work

Runtime: The part of every program that turns a toggle into a popover and back: its daemon, placement and dismissal. Avoid: host, server

Daemon: A program’s background process that shows its popovers and stays running between opens until told to quit. Avoid: server, service, runtime (that’s the whole, not this process)

Compositor: The Wayland compositor the bar and popovers run under, which says where the cursor is and which monitors exist; Hyprland is the only one supported. Avoid: window manager, WM, Hyprland (when any compositor is meant)
